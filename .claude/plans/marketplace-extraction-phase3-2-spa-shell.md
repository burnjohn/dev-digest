# Development Plan — Phase 3.2: catalog SPA shell (Vite + React + hash router + search)

**Execution mode:** multi-agent (lightweight — no separate content-review
pass; verification is command-based, run by the orchestrating session)

## Context

Builds on 3.1's `site/public/{index.json,releases.json,stats.json,
bodies/}` output. This sub-plan (3.2 of 4) creates the `site/` React +
TypeScript + Vite project itself: the hand-written hash-router, the base
layout, the four "core" routes (`#/`, `#/search`, `#/plugin/<name>`,
`#/artifact/<id>`), MiniSearch-backed search, `marked`+`DOMPurify`
markdown rendering, and the plugin detail page's install-command
copy-paste block. The remaining two routes (`#/whats-new`,
`#/getting-started`) and the three bonus features (dependency-graph
viz, badges) are 3.3's job — this sub-plan's routes and components must be
built so 3.3 can add to them without restructuring.

Working directory: `/Users/viptech/dev/ai agent/dev-digest-ai-marketplace`.

## Constraints

From `docs/specs/marketplace-extraction/architecture.md`:

- **Hash routing, no `react-router`** (architecture.md:512-517, resolved
  open question #8): a hand-written `useHashRoute()` hook (~20 lines) that
  reads `window.location.hash`, matches against the fixed six-route list,
  re-renders on the `hashchange` event. Do not add `react-router` or any
  routing library as a dependency.
- **MiniSearch over `index.json`** fields `name`, `description`,
  `keywords`, README body, `SKILL.md` body (architecture.md:325-327) — the
  README/SKILL.md body text comes from 3.1's `bodies/` files, loaded and
  indexed client-side, not server-side.
- **`marked` → `DOMPurify`, always, no exceptions**
  (architecture.md:327-332, and the explicit Invariant at
  architecture.md:571-575): every piece of repository-sourced Markdown
  rendered on the site must go through `DOMPurify.sanitize()` after
  `marked.parse()` before insertion into the DOM (e.g. via
  `dangerouslySetInnerHTML`) — this is a security invariant, not a nice-to-have,
  and applies to README/SKILL.md/CHANGELOG bodies alike.
- **Install command format** is fixed:
  `/plugin install <plugin-name>@dev-digest-ai-marketplace`
  (architecture.md:334-339) — render it verbatim with the real plugin name
  substituted, with a copy-to-clipboard affordance (lab step 6's own
  end-of-lab check: "Copy install копіює правильну команду").
- **i18n scaffolding starts here, content lands in 3.3** — per
  architecture.md:341-347 no interface string may be hardcoded in a
  component. Since the actual `site/src/i18n/en.json` dictionary + `useT`
  hook build-out is scoped to 3.3 in this phase split, this sub-plan's
  components should still avoid literal UI strings where practical (route
  labels, button text) by routing them through a **minimal placeholder**
  `useT` stub (e.g. a hook that returns the key's English fallback text
  directly) so 3.3 only has to swap the stub's internals for the real
  dictionary-backed version, not touch every component again. Document
  this handoff explicitly in the component code (a one-line comment: "i18n
  dictionary lands in Phase 3.3").
- **Package manager: npm** (Stack) — `site/package.json` uses npm,
  `npm ci`/`npm run dev`/`npm run build`/`npm run preview` per the lab's
  own local-verification commands (04-hands-on-lab.md Крок 6).
- **`site/dist/` and `site/public/*.json`/`bodies/` are gitignored**
  (confirmed in root `.gitignore`) — do not commit generated output; only
  source (`site/src/**`, `site/index.html`, `site/package.json`,
  `site/vite.config.ts`, `site/tsconfig.json`, etc.) is committed.
- **English-only prose** in all committed source, comments, and any
  literal fallback text (architecture.md:587-591).
- **No absolute local filesystem paths** in committed code
  (architecture.md AC-8).

From the hands-on lab (Крок 6): local verification is
`npm run build:index && cd site && npm ci && npm run build && npm run
preview` from repo root.

  `site/src/**` tree.
- `react-ui-architecture` — where each piece of `site/src/**` physically

  which do not apply to this separate repo).

  must include per the confirmed test strategy (see Ordered steps step 8):
  the hash-router hook and the search behavior are the two most
  test-worthy units here.

  `index.json`/`releases.json`/`stats.json` shapes (mirror the JSDoc
  contract documented in 3.1's `build-index.mjs`) as shared TS types under
  `site/src/types/catalog.ts`.
- `security` — confirm the `marked`+`DOMPurify` sanitize-before-render
  rule is actually applied at every markdown-rendering call site, not just
  the first one written; this is the skill that flags "did you sanitize
  untrusted HTML" as a systemic check, not a one-time step.

## Ordered steps

1. **Scaffold `site/` as a Vite + React + TypeScript project**
   (`site/package.json`, `site/vite.config.ts`, `site/tsconfig.json`,
   `site/index.html`, `site/src/main.tsx`, `site/src/App.tsx`). Dependencies:
   `react`, `react-dom`, dev deps `typescript`, `vite`, `@vitejs/plugin-react`,
   `minisearch`, `marked`, `dompurify`, `@types/dompurify` (if needed by the
   installed version), `@types/react`, `@types/react-dom`. Add
   `vitest`, `@testing-library/react`, `@testing-library/jest-dom`,
   `@testing-library/user-event`, `jsdom` as dev deps for step 8's tests.
2. **Implement `useHashRoute()`** in `site/src/router/useHashRoute.ts`:
   reads `window.location.hash`, parses it against the six known patterns
   (`#/`, `#/search`, `#/plugin/:name`, `#/artifact/:id`, `#/whats-new`,
   `#/getting-started` — the last two are 3.3's routes but the matcher
   should recognize all six from the start so 3.3 doesn't have to touch
   the router itself), subscribes to `window.addEventListener('hashchange',
   ...)`, cleans up on unmount.
3. **Build the base layout** (`site/src/components/Layout.tsx`): header
   with search entry point, nav, content area — matching the routes above.
   For routes not yet implemented in this sub-plan (`#/whats-new`,
   `#/getting-started`), render a simple "coming in 3.3" placeholder page
   rather than a broken route, so the SPA never dead-ends.
4. **Load `site/public/index.json` etc. at runtime** via a small data hook
   (`site/src/data/useCatalog.ts`) using `fetch()` against the same-origin
   public path — no bundler-time import of the generated JSON (it doesn't
   exist at `site/`-scaffold time; it's produced by `build-index.mjs`
   before `vite build`/`vite dev` runs, consistent with the lab's build
   order).
5. **Implement MiniSearch-backed search**
   (`site/src/search/useSearch.ts` + `#/search` page component): index
   `name`, `description`, `keywords`, and the fetched body text (from
   `bodies/`) fields per architecture.md; results render as cards.
6. **Implement the plugin detail page** (`#/plugin/<name>`): version,
   owner, compatibility floor (from `COMPATIBILITY.md` data surfaced via
   `index.json`), dependency list, composition (agents/skills it ships,
   linking to `#/artifact/<id>` entries), rendered README body
   (`marked` → `DOMPurify`), and the install-command block with a copy
   button.
7. **Implement the artifact detail page** (`#/artifact/<id>`): shows a
   single skill/agent's frontmatter description plus its rendered
   `SKILL.md`/agent-body markdown (same sanitize pipeline), and a link back
   to its owning plugin.
8. **Write tests** (per confirmed test strategy):
   - `site/src/router/useHashRoute.test.ts` (React Testing Library's
     `renderHook`, or a plain hook test) covering: initial hash parse,
     `hashchange` triggers a re-render with the new matched route, an
     unrecognized hash falls back to a documented default (e.g. `#/`).
   - `site/src/search/useSearch.test.ts` or a component test on the
     `#/search` page: given a small in-memory `index.json`-shaped fixture
     (not the real generated file — a literal test fixture is correct here,
     since this is testing search *behavior*, not asserting real catalog
     content), a keyword match returns the expected card entries and a
     non-matching keyword returns zero results.
   - One smoke test on the plugin detail page confirming the install
     command string is rendered verbatim for a given plugin name.
9. **Add `site/README.md`** (brief): what the SPA is, `npm run dev`,
   `npm run build`, `npm run preview`, `npm test`, and a one-line note that
   `npm run build:index` must be run from the repo root first (or is
   already wired into `site`'s own `predev`/`prebuild` npm lifecycle
   script if the implementer chooses to wire it that way — either is
   acceptable, but document whichever choice is made).

## Test plan

Run from `site/` (after `npm run build:index` has been run once from repo
root by the orchestrating session, per the confirmed no-Bash-for-implementer
constraint):

- `npm ci` — installs cleanly, no peer-dependency errors.
- `npm test` (Vitest) — all component/hook tests from step 8 pass.
- `npm run build` — production build succeeds, emits `site/dist/`.
- `npm run preview` — starts a local static server serving `site/dist/`;
  manually confirm (by the orchestrating session, in a browser or via
  `curl`) that `#/`, `#/search`, and at least one `#/plugin/<real-name>`
  route render real data — e.g. all four real plugin names appear
  somewhere reachable from `#/` or `#/search`, not zero/placeholder
  content.
- `npm run dev` — local dev server starts without error (promt #10's
  explicit ask), confirming the dev workflow independent of the production
  build.

**The implementer agent is not expected to have Bash access.** All five
commands above are run by the orchestrating session after the
implementer's changes land; failures are relayed back to the implementer
as a fix-round input rather than assumed self-verified.
