## 1. Context

A reviewer opening a PR today sees the diff and findings but has to manually reconstruct *why* the change exists and *where* the real risk concentrates. The repo already composes a deterministic `PrBrief` (intent, blast radius, mechanically-derived risks, prior-PR history) with **zero LLM calls** after every review run (`brief-composer.ts` via `run-executor.ts`). This feature adds a narrative + prioritization layer on top: `what`/`why`/`risk_level`/`review_focus[]`, generated by **exactly one structured LLM call**, triggered explicitly by the user (`POST /pulls/:id/brief`), persisted alongside the existing deterministic fields, and rendered by enhancing the three existing Overview cards (PR BRIEF/VerdictBanner, INTENT, BLAST RADIUS) plus exactly one new "REVIEW FOCUS — READ THESE FIRST" card.

This plan resolves the spec's four `[NEEDS CLARIFICATION]` items and the Context Folder selection rule, all as approved by the coordinator:

1. **Additive-migration shape:** new `llm` sub-object inside the existing `pr_brief.json` JSONB column — **no new migration**. `Risk` gains nullish enrichment fields (`file`/`line`/`endpoint`/`symbol`/`github_link`).
2. **Bounded-input budget:** soft target ≤8,000 tokens, section-priority drop-order truncation (never a hard reject), precedented on `run-executor.ts`'s `diffBudgetForModel`/`budgetDiff`.
3. **Reference validation/repair:** 3-tier deterministic algorithm (exact match → basename repair → endpoint substring match → drop-reference-keep-prose), zero LLM calls.
4. **Click target:** GitHub blob URL only (`https://github.com/{owner}/{repo}/blob/{sha}/{path}#L{line}`), matching `SymbolImpact.tsx`'s existing convention exactly — no internal Files-changed anchor.
5. **Context Folder selection rule:** repo-level `getContextFolders` + `listDocuments`, ordered by `used_by_agents` descending then alphabetically, each excerpt wrapped in `wrapUntrusted`.

## 4. Project Constraints

- **Additive migrations only** — this feature requires **zero** new migration files; confirmed the `json` JSONB column already accepts any additive shape, all new typing lives in Zod (`contracts/brief.ts`), never in `db/schema/reviews.ts`.
- **`workspace_id` scoping on every query** — `upsertLlmBrief`/`getBrief` both join through `pull_requests.workspace_id`, exactly like the existing `getBrief`. The new `getLatestFindings` read (Step 4) is explicitly workspace-scoped by joining through `reviews.workspace_id`, per `server/AGENTS.md`'s stated invariant for finding reads — see Step 4c for the exact join shape.
- **Adapters only via Container** — `container.llm(provider)`, `container.contextDocs.getContextFolders`/`listDocuments`/`getDocumentContent`, and `container.blast.getBlast(workspaceId, prId)` (a first-class Container getter — `container.ts:139-142`; `BlastService` is lazily instantiated by the container exactly like `repoIntel`/`contextDocs`). `run-executor.ts:462` already calls `this.container.blast.getBlast(...)` from inside this same `reviews` module — the established, sanctioned pattern for reusing another module's service via its Container getter. `BriefGeneratorService` calls `container.blast.getBlast(workspaceId, prId)` directly and reuses its `BlastResponse.blast`/`.history` output as-is — see Step 4c for the exact call. (Resolved per cross-model review Blocking Issue #1 — the prior draft of this plan incorrectly instructed reimplementing blast facts via `repoIntel` to avoid a supposed "cross-module forbidden" import; that import is in fact the sanctioned pattern and reimplementation would have produced needless duplicate blast-computation logic.)
- **`AppError` for all expected failures** — `BriefGeneratorService.generate()` throws `NotFoundError` (missing/cross-workspace PR) and a new `AppError('brief_generation_failed', ..., 502)` (mirrors `onboarding_generation_failed`) on LLM failure, never a raw `Error`.
- **Secrets only via `SecretsProvider`** — no direct secret access in this feature at all; `container.llm(provider)` already encapsulates key retrieval (same as every other LLM-calling module).
- **Shared types → `server/src/vendor/shared/` only** — all new types added to `contracts/brief.ts` (already the home of `PrBrief`/`Risk`/etc.), never duplicated in `client/`.
- **`reviewer-core` stays side-effect-free** — this feature does NOT route through `reviewer-core/reviewPullRequest`; it is a standalone `completeStructured` call structured exactly like `onboarding/service.ts`'s `generateTour`. The one utility reused from `reviewer-core` is `wrapUntrusted` (a pure, side-effect-free string function, confirmed publicly exported from `reviewer-core/src/index.ts:17`) — reviewer-core's zero-I/O invariant is about I/O, not about code reuse of pure helpers, so importing this one function does not violate the constraint.
- **No credentials/instance IDs in `.claude/settings.json`** — not applicable to this feature (no settings file changes).
- **Concurrency-safe read-modify-write on shared state (AC-9/AC-10)** — `pr_brief.json`'s deterministic fields (written by the auto-composer after every review run) and its `llm` field (written only by explicit generate/regenerate) must never clobber each other under concurrent writes. Both `upsertBrief` and `upsertLlmBrief` (Step 2) wrap their read-then-write in `db.transaction()` with `SELECT ... FOR UPDATE` on the `pr_brief` row, so a review-completion and a Regenerate click racing on the same PR serialize instead of silently reverting one side's update (see Step 2 for the transactional rewrite and its concurrency test — resolved per cross-model review Blocking Issue #2).
- **Rate limiting (security A06)** — `POST /pulls/:id/brief` rate-limited per-workspace (not per-IP, matching onboarding's `keyGenerator` pattern) at **3 requests / 1 minute** (same value as `ONBOARDING_RATE_LIMIT` — a paid single-LLM-call action with an identical fan-out risk profile).
- **Untrusted input handling (security A05/AC-18)** — PR title/body, finding rationale, Project Context excerpts all wrapped as data-not-instructions before being placed in the LLM prompt; LLM's structured output is untrusted until §10 validation completes.

### Step 2: Repository split — `upsertLlmBrief` + preserve-on-write `upsertBrief` (transactional)

**Dependencies:** Step 1
**Owned paths:** `server/src/modules/reviews/repository/pull.repo.ts`
**What to do:**

> **Concurrency fix (cross-model review Blocking Issue #2):** the read-then-write pattern below MUST run inside `db.transaction()` with a `SELECT ... FOR UPDATE` row lock on the target `pr_brief` row. Without this, a review-completion (`upsertBrief`) and a Regenerate click (`upsertLlmBrief`) racing on the *same PR* can both read the same pre-image and the later writer silently clobbers the earlier writer's update (a genuine lost-update — not a false alarm; see the review document for the exact interleaving). `Db = PostgresJsDatabase<typeof schema>` already supports `db.transaction()`; this is the first place in this module that uses it.

1. Import `LlmBrief` from `@devdigest/shared` alongside the existing `PrBrief`/`Intent` imports.
2. Modify `upsertBrief` (used by the deterministic auto-composer via `run-executor.ts`) to **preserve** any existing `llm` key rather than blind-overwriting the JSONB column, and to do so transactionally with a row lock:
   ```ts
   export async function upsertBrief(db: Db, prId: string, brief: PrBrief): Promise<void> {
     await db.transaction(async (tx) => {
       const [existing] = await tx
         .select({ json: t.prBrief.json })
         .from(t.prBrief)
         .where(eq(t.prBrief.prId, prId))
         .for('update'); // row lock — serializes against a concurrent upsertLlmBrief on the same prId
       const existingLlm = existing ? PrBrief.partial().safeParse(existing.json).data?.llm : undefined;
       const merged: PrBrief = { ...brief, llm: brief.llm ?? existingLlm ?? null };
       await tx
         .insert(t.prBrief)
         .values({ prId, json: merged })
         .onConflictDoUpdate({ target: t.prBrief.prId, set: { json: merged } });
     });
   }
   ```
   Use `PrBrief.partial().safeParse` (not `.parse`) defensively — a pre-existing row written before this feature has no `llm` key at all, and `safeParse` must not throw on that shape. Note: `.for('update')` on a `select` that may return zero rows (first-ever insert for this PR) is a no-op lock — Drizzle/Postgres allow `FOR UPDATE` on an empty result set; the subsequent `insert ... onConflictDoUpdate` inside the same transaction still serializes correctly against a concurrent first-insert race via Postgres's own unique-constraint conflict handling.
3. Add a new `upsertLlmBrief` function — the ONLY write path the new generation endpoint uses — same transactional row-lock pattern:
   ```ts
   export async function upsertLlmBrief(
     db: Db,
     prId: string,
     llm: LlmBrief,
     enrichedRisks?: Risk[],
   ): Promise<PrBrief> {
     return db.transaction(async (tx) => {
       const [existing] = await tx
         .select({ json: t.prBrief.json })
         .from(t.prBrief)
         .where(eq(t.prBrief.prId, prId))
         .for('update'); // row lock — serializes against a concurrent upsertBrief on the same prId
       if (!existing) {
         // No deterministic brief exists yet (e.g. PR never reviewed) — still
         // persist a well-formed PrBrief shell so the LLM part is not lost.
         const shell: PrBrief = {
           intent: { intent: '', in_scope: [], out_of_scope: [] },
           blast: { changed_symbols: [], downstream: [], summary: '' },
           risks: { risks: enrichedRisks ?? [] },
           history: { history: [] },
           llm,
         };
         await tx.insert(t.prBrief).values({ prId, json: shell });
         return shell;
       }
       const current = PrBrief.parse(existing.json);
       const merged: PrBrief = {
         ...current,
         risks: enrichedRisks ? { risks: enrichedRisks } : current.risks,
         llm,
       };
       await tx.update(t.prBrief).set({ json: merged }).where(eq(t.prBrief.prId, prId));
       return merged;
     });
   }
   ```
   The optional `enrichedRisks` parameter is consumed by `BriefGeneratorService` (Step 4k) to merge the LLM-enriched `risks[]` (with `file`/`line`/`endpoint`/`symbol`/`github_link`) into the same transaction as the `llm` write — a single atomic transaction covers both field groups, avoiding a second separate read-modify-write that would reopen the same race this step just closed.
4. `getBrief` (existing function) needs NO change — it already does `PrBrief.parse(row.json)`, which now additionally validates/passes through the nullish `llm` key transparently.

**Verify:**
- [ ] Compiles (`pnpm typecheck`)
- [ ] Hermetic test (new): `upsertBrief` called twice — first with `llm: null`, generation writes `llm` via `upsertLlmBrief`, then a second `upsertBrief` call (simulating a new review run) — assert the `llm` key survives (AC-10)
- [ ] Hermetic test: `upsertLlmBrief` on a PR with no existing `pr_brief` row creates a well-formed shell (edge case: "PR has no prior review" from spec §16)
- [ ] **Concurrency test (new, cross-model review Blocking Issue #2):** fire `upsertBrief(db, prId, newDeterministicBrief)` and `upsertLlmBrief(db, prId, newLlmBrief)` concurrently (both reading the same pre-image window — e.g. via two overlapping `Promise.all` calls against a real transactional DB, or an integration-level test if a hermetic mock can't model row-lock serialization) against the same `prId`; assert that after both resolve, the final row contains **both** the new deterministic fields **and** the new `llm` field — neither writer's update is lost. This test requires a real Postgres connection (row locks are meaningless against a mock) — place it in `server/test/brief-generator.it.test.ts` (Step 10) if `pull.repo.ts`'s existing test file is hermetic-only; note the cross-reference here so Step 10 doesn't skip it.

### Step 9: `useGenerateBrief` hook + `OverviewTab` wiring (empty/loading/cached/error states)

**Dependencies:** Step 5 (real endpoint), Step 6 (ReviewFocusCard), Step 7 (IntentCard), Step 8 (VerdictBanner) — this step is the integration point and cannot start until all four land
**Owned paths:** `client/src/lib/hooks/reviews.ts` (add `useGenerateBrief` only — do not touch other hooks in this file), `client/src/app/repos/[repoId]/pulls/[number]/_components/OverviewTab/OverviewTab.tsx`
**What to do:**

> **AC-14 fix (cross-model review Blocking Issue #3):** the current `OverviewTab.tsx:110` gates the ENTIRE PR BRIEF section on `latest?.verdict` (`{latest?.verdict && (<section>...<VerdictBanner ... /></section>)}`) — for a PR with **zero reviews**, nothing renders in that slot today, not even a placeholder. Implementing this step literally on top of that existing gate (i.e., adding the empty-state branch *inside* the `{latest?.verdict && (...)}` block) would leave the slot blank for a zero-review PR and silently regress AC-14 ("WHEN neither a generated brief nor an in-progress generation exists for a PR, the PR BRIEF card slot SHALL show the 'No brief yet → Generate brief' empty state — never a blank card"), which is exactly the spec §16 edge case "PR has no prior review / no findings yet." This step explicitly requires REMOVING that outer gate.

1. Add to `hooks/reviews.ts`:
   ```ts
   export function useGenerateBrief(prId: string | null | undefined) {
     const qc = useQueryClient();
     return useMutation({
       mutationFn: () => {
         if (!prId) throw new Error('prId required');
         return api.post<PrBrief>(`/pulls/${prId}/brief`);
       },
       onSuccess: (brief) => {
         qc.setQueryData(["pr-brief", prId], brief); // instant cache update, no refetch needed
       },
     });
   }
   ```
2. In `OverviewTab.tsx`, **restructure the top-level PR BRIEF section to remove its dependency on `latest?.verdict`** — replace the current:
   ```tsx
   {latest?.verdict && (
     <section>
       <SectionLabel icon="FileText">PR Brief</SectionLabel>
       <VerdictBanner ... />
     </section>
   )}
   ```
   with an unconditional wrapper that always renders the `<section>`/`<SectionLabel>` and then branches internally on the brief/verdict data:
   ```tsx
   <section>
     <SectionLabel icon="FileText">PR Brief</SectionLabel>
     {brief?.llm ? (
       <VerdictBanner
         verdict={latest?.verdict ?? "comment"}
         summary={latest?.summary ?? null}
         score={latest?.score ?? null}
         findingsCount={latest?.findings.length ?? 0}
         blockers={blockers}
         costUsd={costUsd}
         what={brief.llm.what}
         why={brief.llm.why}
         riskLevel={brief.llm.risk_level}
         tokensIn={brief.llm.tokens_in}
         tokensOut={brief.llm.tokens_out}
         onRegenerate={() => generateBrief.mutate()}
         regenerating={generateBrief.isPending}
         generationError={generateBrief.isError ? generateBrief.error.message : null}
       />
     ) : latest?.verdict ? (
       // Deterministic review verdict exists but no LLM brief generated yet —
       // show the existing verdict banner AND the empty-state CTA together
       // (verdict content is real data, not blank; the LLM part is what's missing).
       <>
         <VerdictBanner
           verdict={latest.verdict}
           summary={latest.summary}
           score={latest.score}
           findingsCount={latest.findings.length}
           blockers={blockers}
           costUsd={costUsd}
         />
         <BriefEmptyState onGenerate={() => generateBrief.mutate()} generating={generateBrief.isPending} error={generateBrief.isError ? generateBrief.error.message : null} />
       </>
     ) : (
       // Zero reviews AND no LLM brief — pure empty state, never a blank card (AC-14).
       <BriefEmptyState onGenerate={() => generateBrief.mutate()} generating={generateBrief.isPending} error={generateBrief.isError ? generateBrief.error.message : null} />
     )}
   </section>
   ```
   `BriefEmptyState` is a small local component (co-located in `OverviewTab.tsx` inline, or extracted to a tiny `BriefEmptyState.tsx` in the same folder if it exceeds ~20 lines — owned by this step either way since it's part of the wiring, not a new independent card per spec AC-19's "exactly one new card"; the empty state is a STATE of the existing PR BRIEF slot, not a second new card) rendering the "No brief yet → Generate brief" card per spec §5 State 1, plus an inline error + retry when `error` is set (AC-13), plus a non-blocking in-progress indicator when `generating` is true.
3. **Loading state**: while `generateBrief.isPending`, if `brief?.llm` already exists, keep showing its content via `regenerating={true}` on `VerdictBanner` (handled above); if there was never a prior brief, `BriefEmptyState` shows its own in-progress indicator instead of the "Generate brief" button.

5. **Error state**: `generateBrief.isError` → surfaced via `generationError` on `VerdictBanner` (when `brief?.llm` exists — AC-12) or via `BriefEmptyState`'s `error` prop (when no brief ever existed — AC-13); in both cases the last-good content (if any) stays visible, never cleared.
6. Do not alter the existing Intent/Blast rendering branches (`displayIntent`/`blastNode` logic) beyond passing the now-enriched `brief?.risks` through unchanged — that data flow already exists.
